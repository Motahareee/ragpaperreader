PaperChat: A Fully Local RAG System for Scientific Literature — Design and Evaluation

Systems evaluation report · accuracy, latency, memory, and scalability
Summary PaperChat is a fully local, privacy-preserving retrieval-augmented generation (RAG) system for question-answering over a folder of PDF papers, packaged as a single portable application. This report evaluates three design choices empirically: (1) a lightweight bundled sentence encoder vs. a stronger alternative, (2) dense cosine retrieval vs. hybrid dense+sparse retrieval, and (3) a brute-force in-memory vector store vs. the assumption that a dedicated vector database is necessary at this scale. Measurements were taken on a 5-paper, 226-chunk test corpus spanning multiple ML subfields (Transformers, optimization, language pretraining, computer vision, regularization) to test topic-overlap effects that a single-paper or single-topic corpus cannot surface.

1. System Design

Everything runs in a single process with no external server or database: PDF parsing and chunking (PyMuPDF, with a column-aware heuristic for two-column academic layout), a bundled GGUF sentence encoder run through llama.cpp, a numpy-array vector store persisted as a JSON sidecar, and a local instruct LLM for answer generation with citations mapped back to exact page/bounding-box locations for passage highlighting in the source PDF.

Figure 1. PaperChat system architecture. Indexing (top row) and query-answering (bottom rows) share the encoder and vector store. No network call occurs except a one-time download of instruct-model weights on first launch (not shown); all indexing, retrieval, and answering happen entirely on-device thereafter.

2. Evaluation Methodology

Three retrieval variants were compared under an identical harness: (a) the shipped system — MiniLM-L6-v2 (GGUF, Q8_0) with cosine similarity; (b) an encoder swap to bge-small-en-v1.5 (GGUF, Q8_0), same retrieval logic; (c) a hybrid retrieval variant keeping MiniLM but fusing cosine and BM25 rankings via Reciprocal Rank Fusion (k=60).

Two accuracy sets were used, both spanning all 5 papers. The first is a hand-verified golden set (n=12) built by confirming each answer's (document, page) by direct inspection of the source PDF. One question originally in this set ("How is positional information added to the input embeddings?") was reclassified into the hard set after expanding the corpus made it genuinely ambiguous — it began competing with BERT's own positional-embedding discussion, a concrete example of retrieval degrading as topically-overlapping documents are added. The second, hard set (n=11), was constructed specifically to include cross-document and keyword-heavy questions verified to fail under plain cosine retrieval, to obtain a discriminating signal that a curated "already works" set cannot provide.

Hardware caveat: all measurements were taken on an emulated Linux ARM64 sandbox, not the target Apple Silicon deployment target (no Metal acceleration available). Relative comparisons between variants below are reliable; absolute latency numbers should be re-measured on target hardware before being cited as production figures.

3. Results

3.1 Accuracy

VariantGolden set (n=12)Hard set (n=11)
MiniLM + cosine (shipped)100% (12/12)27% (3/11)
bge-small + cosine83% (10/12)64% (7/11)
MiniLM + hybrid (cosine + BM25)100% (12/12)64% (7/11)

No single variant dominates. bge-small trades golden-set accuracy for a large hard-set gain — a real, reproducible gap (10/12 vs. 12/12) that only appeared once the corpus grew to 5 topically-varied papers, contradicting the general MTEB-benchmark expectation that bge-small should outperform MiniLM outright. Hybrid retrieval is the strictly better overall choice of the three: it preserves MiniLM's full golden-set accuracy while matching bge-small's hard-set improvement, more than doubling the shipped system's hard-set recall (27% → 64%). The corpus-scale effect itself is a finding worth stating plainly: cosine-only accuracy degraded sharply as more topically-adjacent documents were added (recall the reclassified positional-embedding question in §2) — a discriminating hard set is necessary precisely because this degradation is invisible to any golden set built against a small corpus.

Brute-force numpy search stays under 80 ms p95 even at 500K synthetic 384-dim vectors — over 2,000× the actual corpus used in this evaluation (226 chunks) and orders of magnitude beyond any realistic paper-folder corpus. This provides empirical support for the design decision to forgo a dedicated vector database (e.g. Chroma, FAISS), which was originally motivated by packaging simplicity rather than performance.

3.5 External Validation (Qasper)

Both accuracy sets above are self-authored, which risks unconsciously tuning the corpus/questions toward favorable results. As an independent check, 20 questions were sampled from Qasper (Dasigi et al. 2021 — evidence-grounded QA over NLP papers, questions written by annotators who had only read the abstract) across 10 papers. Critically, the actual PDFs were fetched from arXiv using Qasper's paper IDs and re-indexed through our own pipeline from scratch — not Qasper's pre-parsed text — so this tests the real system, parser included. A hit was scored when a retrieved chunk had ≥60% word-overlap with Qasper's independently-annotated evidence paragraph (exact-text matching isn't meaningful here, since our chunk boundaries differ from Qasper's own paragraph parsing).

VariantRecall@5 (n=20)
MiniLM + cosine (shipped)50% (10/20)
bge-small + cosine50% (10/20) — tied
MiniLM + hybrid (cosine + BM25)60% (12/20)

All three shipped-system numbers are markedly lower than the self-authored golden set's 100%, as expected — this sample wasn't curated to already work. Hybrid retrieval's improvement (50% → 60%) holds up on this unbiased external sample, corroborating the same finding from the self-authored hard set (§3.1) rather than being an artifact of how that set was built — meaningfully stronger evidence for shipping it. bge-small shows no advantage here, ties MiniLM exactly, in contrast to its hard-set result — a reminder that encoder comparisons are corpus-dependent and don't reliably generalize across samples. Inspecting a zero-overlap cosine miss ("What is the seed lexicon?", paper 1909.00694) showed a genuine cross-document confusion failure: all 5 retrieved chunks came from an entirely unrelated paper in the sample (about word-ordering conventions in online text), not merely the wrong passage within the right paper. Short, low-context questions — common in Qasper by construction, since annotators wrote them having only read the abstract — appear especially vulnerable to this.

4. Interpreting These Numbers

Taken at face value, 50-60% recall@5 on the external Qasper sample reads as mediocre, and it is worth being direct about that rather than letting the framing around it do the work. Several factors bear on how that number should be read, without erasing it as a real limitation:

  • The small local encoder is a deliberate tradeoff, not an oversight. A 384-dim, torch-free, CPU-friendly encoder was chosen specifically to keep the app small and dependency-light enough to package as a single portable executable (§1). A larger or cloud-hosted embedding model would likely score meaningfully higher, at the cost of the packaging/privacy properties that motivate this system in the first place.
  • Both accuracy sets are deliberately adversarial, not representative of typical use. The hard set was built by actively hunting for failure cases; Qasper's questions were written by annotators who had only read the abstract, so many are short and low-context by construction. A real user querying their own topically-coherent stack of papers (not 5-10 papers spanning unrelated subfields) should see less cross-document confusion than either stress test induces.
  • The hit metric is strict and binary. A miss means the exact right passage was outside the top-5 — it gives no credit for "right paper, adjacent chunk" or partial evidence overlap. Practical usefulness is likely somewhat better than the raw recall number implies.
  • The system is designed to fail soft. The generation prompt (§1) explicitly instructs the model to say it lacks enough information rather than guess when retrieved context doesn't contain an answer — so a retrieval miss more often surfaces as an honest non-answer than a confident hallucination, a materially softer failure mode than the recall number alone conveys.
  • The best-measured variant is not the shipped one. Every "MiniLM + cosine" row above is the actual current app; hybrid retrieval, which outperforms it consistently across all three evaluations (§3.1, §3.5), exists only in this benchmark suite. The more urgent gap this report surfaces isn't "can retrieval be improved" — it's "the improvement is already measured and not yet shipped."

5. Discussion & Limitations

  • The golden/hard-set split highlights a methodological point worth stating explicitly in any paper: curated "it works" test sets cannot measure comparative accuracy; discriminating evaluation requires deliberately adversarial cases.
  • Expanding the corpus from 2 to 5 papers changed the accuracy story materially — both by causing a previously-easy question to fail (topic overlap with a new document) and by surfacing a real bge-small vs. MiniLM accuracy gap invisible at smaller scale. This is itself evidence that accuracy results at n=2 papers were not representative; results at n=5 (and the Qasper sample at n=10) should still be treated as an early signal, not a generalizable claim, at the scale of a real benchmark suite.
  • The bge-small single-query latency figure was unstable across runs (203ms → 14.6ms) and should be re-measured with a proper warmup + repeated-trial protocol before being used to argue anything about encoder choice on latency grounds — this benchmark's first pass made exactly the single-shot-measurement mistake it should have avoided.
  • The Qasper word-overlap hit metric (§3.5) is an automatic proxy, not exact ground truth: a genuinely correct retrieval whose evidence happens to straddle two of our chunk boundaries could score below the 60% threshold in either chunk alone and register as a false miss. The 50-60% figures should be read as conservative estimates, not precise ones — and at n=20 questions, individual misses can swing the headline number by 5 points.
  • All results were gathered on non-target hardware (Linux ARM64 sandbox); absolute latency claims require re-measurement on Apple Silicon before publication.
  • Hybrid retrieval (cosine + BM25 via RRF) is the best-supported change to actually ship: it strictly dominates plain cosine (equal or better on all three evaluations) and avoids bge-small's golden-set regression, at a small latency cost (7.8ms vs. 0.46ms search-only) that is negligible next to LLM generation time.
