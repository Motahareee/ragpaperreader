PaperChat: A Fully Local RAG System for Scientific Literature — Design and Evaluation

Systems evaluation report · accuracy, latency, memory, and scalability
Summary PaperChat is a fully local, privacy-preserving retrieval-augmented generation (RAG) system for question-answering over a folder of PDF papers, packaged as a single portable application. This report evaluates three design choices empirically: (1) a lightweight bundled sentence encoder vs. a stronger alternative, (2) dense cosine retrieval vs. hybrid dense+sparse retrieval, and (3) a brute-force in-memory vector store vs. the assumption that a dedicated vector database is necessary at this scale. All measurements were taken on a 2-paper, 71-chunk test corpus.

1. System Design

Everything runs in a single process with no external server or database: PDF parsing and chunking (PyMuPDF, with a column-aware heuristic for two-column academic layout), a bundled GGUF sentence encoder run through llama.cpp, a numpy-array vector store persisted as a JSON sidecar, and a local instruct LLM for answer generation with citations mapped back to exact page/bounding-box locations for passage highlighting in the source PDF.

Figure 1. PaperChat system architecture. Indexing (top row) and query-answering (bottom rows) share the encoder and vector store. No network call occurs except a one-time download of instruct-model weights on first launch (not shown); all indexing, retrieval, and answering happen entirely on-device thereafter.

2. Evaluation Methodology

Three retrieval variants were compared under an identical harness: (a) the shipped system — MiniLM-L6-v2 (GGUF, Q8_0) with cosine similarity; (b) an encoder swap to bge-small-en-v1.5 (GGUF, Q8_0), same retrieval logic; (c) a hybrid retrieval variant keeping MiniLM but fusing cosine and BM25 rankings via Reciprocal Rank Fusion (k=60).

Two accuracy sets were used. The first is a hand-verified golden set (n=8) built by confirming each answer's page by inspection — but because it was curated against the shipped system, it cannot show accuracy differences between variants (all three score 100% on it). A second, harder set (n=6) was constructed specifically to include cross-document, keyword-heavy questions verified to fail under plain cosine retrieval, to obtain a discriminating signal.

Hardware caveat: all measurements were taken on an emulated Linux ARM64 sandbox, not the target Apple Silicon deployment target (no Metal acceleration available). Relative comparisons between variants below are reliable; absolute latency numbers should be re-measured on target hardware before being cited as production figures.

Hybrid retrieval recovered a miss common to both pure-cosine variants — a keyword-heavy query ("What dataset was used for the English-to-German translation task?") — consistent with the known failure mode of dense embeddings under-weighting exact lexical matches that sparse retrieval catches directly.

Brute-force numpy search stays under 80 ms p95 even at 500K synthetic 384-dim vectors — orders of magnitude beyond any realistic paper-folder corpus. This provides empirical support for the design decision to forgo a dedicated vector database (e.g. Chroma, FAISS), which was originally motivated by packaging simplicity rather than performance.

4. Discussion & Limitations

  • The golden/hard-set split highlights a methodological point worth stating explicitly in any paper: curated "it works" test sets cannot measure comparative accuracy; discriminating evaluation requires deliberately adversarial cases.
  • Corpus size (2 papers, 71 chunks) is small; results on accuracy should be treated as a pilot signal, not a generalizable claim, without a larger benchmark (e.g. Qasper).
  • The bge-small latency anomaly is unresolved and worth root-causing before drawing conclusions about encoder choice on latency grounds.
  • All results were gathered on non-target hardware (Linux ARM64 sandbox); absolute latency claims require re-measurement on Apple Silicon before publication.
