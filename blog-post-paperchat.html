Building PaperChat: a private, local RAG chatbot for your research papers

A weekend-scoped project to answer one question: can I ask my own laptop about a folder of PDFs, without a single byte leaving the machine?
RAG local LLM privacy macOS

I wanted something simple: drop a folder of research papers on my desk, double-click one file, and ask it questions — "what optimizer did they use," "how does this compare to the baseline," "which section talks about limitations." No uploading PDFs to a website, no account, no wondering where my unpublished drafts end up. Just a chatbot that reads the folder it's sitting in.

That's the whole idea behind PaperChat. This post is the log of actually building it — what exists already, what was missing, and the decisions that shaped the design.

Does this already exist?

Mostly, yes. Tools like AnythingLLM, GPT4All's LocalDocs, PrivateGPT, and Kotaemon already do local, private, folder-based RAG chat. Before writing a line of code, it was worth checking whether any of them just... solved this.

None of them quite fit the exact shape I wanted, for three concrete reasons:

  1. No true zero-install distribution. Every one of them wants Docker, a multi-step installer, a Python environment, or a separate Ollama process running alongside. None is "one file, drop it anywhere, done."
  2. Weak handling of academic PDFs. Multi-column layouts, equations, and reference lists trip most of them up — GPT4All's own docs suggest running a separate cleanup tool before ingestion.
  3. Inconsistent citations. Some tools cite a filename; a couple (Kotaemon, notably) highlight the retrieved passage in a PDF viewer, which is exactly the experience I wanted, but bundled with everything else I didn't.

So: a genuinely portable, zero-setup app that parses academic PDFs reasonably well and highlights the exact passage it's citing, directly in the document. Narrow enough to actually build.

The shape of the thing

Everything runs in one process, in one language, with no server the user ever has to think about:

  • PDF parsing — PyMuPDF pulls out text blocks with page number and exact bounding box. A column-detection heuristic sorts blocks so two-column academic layout reads top-to-bottom, left-column-then-right-column, instead of zig-zagging across the page.
  • Embeddings — a small GGUF embedding model, bundled directly inside the app. Running it through llama.cpp instead of the more common sentence-transformers/torch stack means no multi-gigabyte torch dependency to fight with during packaging.
  • Vector store — no database at all. Just a numpy array and a metadata file, living in a quiet .ragindex/ folder next to the papers. Brute-force cosine similarity is plenty for a folder of PDFs, and it means one less thing to install or corrupt.
  • The answering model — a mid-size instruct model (Qwen2.5-7B), downloaded once on first launch and cached forever after. This was the one deliberate compromise on "fully offline": the very first run needs internet to fetch generic model weights. Your papers and every question you ever ask never leave the machine, on that run or any other.
  • The highlight — when the model answers, it cites numbered excerpts. Click one, and the PDF panel (rendered with pdf.js, the same engine Chrome and Firefox use) jumps to the page and draws a highlight box over the exact retrieved passage.
Why auto-download the LLM instead of bundling it? A fully bundled small model (~3B params) would mean zero internet, ever — appealing, but the answer quality for synthesizing across multiple papers was noticeably weaker. Since the download only ever touches generic model weights, never your documents, the one-time setup cost felt worth trading for materially better reasoning.

The Mac-specific wrinkle nobody warns you about

The plan was "package it as one file, drop it in a folder, double-click it." Turns out that on macOS, double-clicking an app from Finder does not set its working directory to the folder it's sitting in — Finder launches it from somewhere else entirely. If I hadn't caught this, the app would have opened, looked fine, and quietly indexed the wrong folder every single time.

The fix: instead of trusting the working directory, the app looks up its own .app bundle's location on disk and treats that folder as the one to index. It's a small detail, but it's the difference between "drop it in a folder and it works" and "drop it in a folder and it mysteriously doesn't."

Testing a RAG pipeline is its own small puzzle

The deterministic parts — PDF parsing, chunking, the vector store — get a normal pytest suite: synthetic fixture PDFs, known inputs, exact expected outputs. Nothing unusual there.

The interesting part is testing retrieval quality, which isn't a pass/fail thing in the usual sense. The approach that worked: build a small golden set of real questions against a real paper, verify by hand that the answer to each one genuinely lives on a specific page, then assert the retrieval step actually surfaces that page in its top results. It's a regression baseline, not a claim of objective correctness — but it catches exactly the failure mode that matters: "the right passage stopped showing up after that refactor."

That process was also honest about the small embedding model's ceiling — a few plausible test questions simply didn't retrieve the right page, and got dropped from the golden set rather than papered over. Worth knowing going in: a tiny, fast, CPU-friendly embedding model trades away some retrieval precision, and that's a real, visible limitation, not just a theoretical one.

Where it stands

The core pipeline — parse, chunk, embed, retrieve, answer, cite, highlight — is built and passes an end-to-end test against a real 15-page paper, with the model correctly answering a question and citing the exact right passage. The pytest suite covers the deterministic logic plus a retrieval-quality regression check.

What's still ahead: building and running the actual packaged .app on real macOS hardware (the tricky bits so far were all verified against the underlying logic, not the finished GUI), and eventually a Windows/Linux build once the Mac version is solid.

If you're building something similar: the biggest lesson so far isn't about RAG at all — it's that "just drop a file in a folder and run it" turns out to hide several small, very specific platform assumptions (working directories, Gatekeeper, packaging heavy ML dependencies) that are easy to miss until you actually try to ship it.
